## 0. Governing decisions

- **Extend `packages/integrations`, never fork it.** Its `IntegrationOutcome` type already encodes the directive's honesty rule: only `source:"provider"` can be `verified`; every `Mock*` adapter is physically incapable of claiming success. All social/marketing providers return this union. Business logic consumes normalized domain types; **raw provider payloads stop at the adapter edge.**
- **Credential reality is stated, not papered over.** Workspace has `META_APP_ID`/`META_APP_SECRET`/`WHATSAPP_PHONE_NUMBER` but **no access token and no phone-number id**; no Vercel-env probe was performed. Therefore WhatsApp/FB/IG ships as: adapter + sandbox tests + setup screen + webhook ingestion verified against synthetic signed payloads. **No claim that live messaging or live publishing works.** The register's "CREDENTIALS PROVISIONED" line is corrected to match this evidence.
- **No unofficial automation, ever.** WhatsApp Web scraping/simulation, private-message scraping, and simulated publishing are excluded by design (no code path, not just policy text).
- **Webhook ingestion is global, then scoped.** Meta's handshake and POST arrive without a session; routes verify `X-Hub-Signature-256` (HMAC-SHA256 over the RAW body with the app secret) before parsing, deduplicate by provider id (Meta retries for up to 7 days in batches up to 1000 — duplicates are a guarantee, not an edge case), persist raw events, and only then fan out into tenant scope resolved from `phoneNumberId`/`pageId` registry rows. Unroutable-but-authentic events park in an operator-visible queue; forged events are dropped with 200 + audit (Meta redrives non-200s forever).
- **Messaging windows and opt-outs are computed, never stored-and-trusted.** The 24-hour customer-service window derives from the last inbound message timestamp; template-only-when-window-closed and opt-out suppression are enforced server-side on every send.
- **Drafting and publishing are separate objects.** `ContentPost` (draft/approved) and `PublishJob` (attempt against a provider) are distinct rows; a generated or approved draft is never rendered as published. "Published" requires a provider reference from a `verified` outcome. Instagram has no native scheduling — our own queue is the scheduler (documented, with the 100 API-posts/24h ceiling as a configured budget, not a guess).
- **Event tracking gets its own append-only table** (`MarketingEvent`) rather than bloating `ActivityEvent`: different consent surface, different volume, different retention question. Dedup by unique event id; share-link clicks carry a server-minted `clickId` so retries never double-count. Analytics consent gate: `Contact.marketingConsent` must be true to attach identifiable events to a contact; otherwise the event is stored de-identified (no contactId).
- **AI integration points are seams, not features.** `QuickReply` + `ContentPost` payloads reserve an `aiDraft` provenance flag and the inbox exposes a typed "suggestion slot"; no AI provider is wired in this phase (register: SPECIFICATION status; stays honest).

## 2. Data model (migration 26: `20261101000000_agent03_social_commerce_marketing`)

## 3. Adapter contract (module A)

`packages/integrations/src/social.ts` (new; exported from index):

- `interface SocialChannelAdapter { readonly name: string; readonly isLive: boolean; capabilities(): ProviderCapability[]; verifyConnection(cred): Outcome<ConnectionFacts>; fetchConversationPage(...): Outcome<NormalizedMessage[]>; sendSessionMessage(...): Outcome<SendReceipt>; sendTemplate(...): Outcome<SendReceipt>; markConversation(...): Outcome<unknown>; publishPost(...): Outcome<PublishedRef>; }` — every method returns `IntegrationOutcome<T>`; `MetaWhatsAppAdapter` (Graph fetch w/ 10s timeout cap per register rule), `MetaFbPageAdapter`, `MetaInstagramAdapter` (both stacks), and `MockSocialChannel` (isLive:false, no I/O, everything `unverified("mock", …)`).
- Normalized domain shapes (`NormalizedMessage`, `SendReceipt`, `PublishedRef`) defined package-side; webhook parsing lives in apps/web (`services/integrations/webhooks.ts`) and produces normalized events before touching business tables.
- Token lifecycle: Meta system-user tokens are long-lived but revocable; `verifyConnection` probes the debug-token endpoint (sandbox: deterministic fake), errors classified `AUTH` → connection flips ERROR + operator banner; disconnect = status DISCONNECTED + delete credentialCiphertext + park inbound (no message loss claim for provider-side history).
- Rate/retry: adapter declares per-provider budgets (documented constants from fetched docs: 100 IG API posts/24h; messaging tier = "provider-reported", reactive 429 backoff with `Retry-After`, PublishJob exponential retry 1m/5m/25m/2h/6h then ABANDONED with errorClass — nothing auto-retried past credential errors). Health = last successful call + webhook receipt freshness, surfaced in the setup screen.

## 4. Webhook routes (apps/web)

- `GET/POST /api/integrations/meta/webhook` — handshake echo + signature verify (raw body), shared by all Meta channels; POST handler persists `IntegrationWebhookEvent` (dedup) and applies synchronously where cheap (message upsert, status update), routes by `phoneNumberId`/`pageId` from connection registry. Everything returns 200 fast. `x-tenant-subdomain` irrelevant here (global endpoint); no session; the signature IS the authentication.
- `POST /api/integrations/meta/lead-webhook` (Instant Form / lead gen) — same spine.
- Outbound send = staff actions only (`converseInboxAction` → `INBOX_CONVERSE` + window/template/opt-out checks server-side), never exposed publicly. AI suggestion slot: `ConversationMessage.aiDraft` provenance only in this phase.

## 5. UI (Phase 3)

`/app/inbox` (conversation list w/ filters: channel, status, assignee, label, unread; thread view with customer+order context panel fed by AGENT 02 timelines; composer with window-state hint ("template only — 24h window closed"), quick replies, notes, assign, label, convert-to-lead/quotation/order actions reusing 2A/2B APIs; unanswered = `open && !assigned && lastInboundAt oldest` list + response-time stats; all four required states rendered), `/app/marketing` (campaigns, content calendar grid, post composer with draft→approve→schedule→publish flow, media library w/ Blob-seam upload, share-link + campaign tracking panel, per-link event counts), `/app/settings/integrations` (provider cards from live capability matrix, connect/verify/disconnect flow with `INTEGRATIONS_MANAGE`, connection health + webhook freshness + last-error diagnostics sanitized, sandbox banner whenever adapter.isLive false).

## 6. Tests (required areas)

1. Journey: campaign link (UTM) → product page view event → enquiry/conversation → lead → order → payment-verified → fulfillment event chain; consent gate verified on both branches. 2. Webhook: valid signature accepted, forged/replayed rejected, missing 401; dedup on provider retries (same eventId twice → one row). 3. Duplicate-marketing-event idempotent replay. 4. Expired/revoked token → classified, connection ERROR, outbound refused. 5. Failed publishing: retry ladder → ABANDONED, draft stays draft. 6. Rate limit 429 honored. 7. Disconnected integration: inbound parked, outbound refused, UI state. 8. Tenant isolation: connection/Conversation/MarketingEvent forged-tenant refusals + webhook routing cannot cross tenants + harness covers new tables via dynamic RLS test. 9. Role matrix: SALES cannot manage connections; VIEWER read-only; SUPPORT none. 10. Setup screen renders SANDBOX truthfully (isLive false ⇒ banner, no success claim). Sandbox provider fixtures = signed payloads generated with a test app secret (real HMAC vectors, mocked transport).

## 7. Boundaries & owner asks

Owner must supply: `WHATSAPP_ACCESS_TOKEN` + `WHATSAPP_PHONE_NUMBER_ID` (system-user token recommended), complete Meta app review per capability, set `INTEGRATION_SECRET` (+ rotate to KMS decision), public HTTPS domain for webhook registration, ads-reporting decision before that adapter leaves interface-only. No live provider call is executed from this workspace; no external approval is claimed. Analytics retention/purge policy for `MarketingEvent` = open owner decision (DPO design-only rule).
